Factored AI & Data Hackathon 2026 · LATAM Bank dataset

Expediente Vivo v2

Complaint and dispute handling with controlled AI. We keep the team's v1.4 foundation and add machine learning where the data supports it, an investigator agent for the back office where the 16-day delay lives, and a serverless AWS deployment that costs almost nothing when idle.

01Summary and decisions

Customers write in Spanish or Portuguese about a charge or fee they dispute. The system understands the request, finds the exact charge among the customer's own transactions, checks it against data, and picks one of three lanes by rule: A resolve now with the data, B open a complete case with a promised date, or C hand to a person with a structured file. For lane B money disputes, an investigator agent gathers evidence through read-only tools and hands an analyst a cited report and a recommended resolution. The analyst decides. Every decision becomes a label that retrains the models.

The language model reads and writes. Machine learning ranks and scores. Rules in code decide. People approve anything that touches money. Nothing moves money.

From v1.4, kept

Rules decide, the model never does. Tool gateway, lanes A/B/C, completeness rules, promise clock, judge mode, failure switches.

New in v2

Transaction ranker, calibrated classifier, risk evidence, investigator agent, learning loop, planted-scenario evaluation.

Deployment

Lambda, API Gateway, DynamoDB, Step Functions, Bedrock. Scales to zero; about 2 USD a month idle.

03Principles and scope

  1. Data prepares the facts. Curated tables with quality contracts feed everything else.
  2. ML ranks and scores. Each model outputs a probability or evidence, never an action.
  3. Rules decide. Lane choice, handoff triggers and hard limits live in versioned YAML, tested with adversarial cases.
  4. GenAI understands and explains. Extraction, clarification, drafting, investigation reports. Every claim cites a record.
  5. People approve. Anything that would move money or change an account goes to an analyst. Card blocks require the customer's explicit confirmation.

05Machine learning

D3

Three models plus a learning loop. Each has real ground truth, a baseline to beat, and a fallback if it doesn't.

M1 · Transaction ranker

Customers describe charges loosely: "como 450 en el super el 12". v1.4 finds the charge with a rule. M1 scores every candidate charge in the customer's window and returns calibrated probabilities, so the system knows when it is sure, when to offer choices, and when to ask.

ItemM1 specification
InputG1 slots (any may be missing) + the customer's transactions in the window from DynamoDB
FeaturesAmount gap as log ratio after FX to the claimed currency; day gap in the customer's local time; merchant similarity (character trigrams + alias table); merchant category match; card last-4 match; status (approved, pending, reversed); "round number" flag; amount rank within window; missing-slot flags
ModelLightGBM LambdaRank; top-1 probability from softmax over scores, calibrated with isotonic regression on validation
Training dataReal transactions from ~20k sampled customers. For each target, generated complaint slots with realistic noise: rounded amounts, ±1–5 day errors, merchant nicknames, 30–50% missing fields, wrong card. Hard negatives: same merchant on other days, same amount at other merchants. 300 end-to-end ES/PT messages run through G1 as a second test
Baselinev1.4 rule: date ± 1 day, amount ± 5%, merchant contains the text
MetricsTop-1 accuracy, recall@3, wrong-confirmation rate (unsafe), clarification rate, no-match detection on planted "charge doesn't exist" cases; by language and country
FallbackIf M1 doesn't beat the rule on wrong confirmations, the rule stays primary and M1 is reported as an experiment

M2 · Calibrated intent classifier

v1.4's model is kept: multilingual embeddings plus logistic regression over the nine classes. Three changes make it defensible:

  • Test set the model never saw in any form. 150 messages the team writes by hand (ES and PT, all three countries, typos, short and long) plus 30 adversarial ones. Training text comes from two different generator prompts so the model doesn't just learn one generator's style.
  • Calibration. Temperature or isotonic scaling; expected calibration error reported.
  • Thresholds from data. The accept / ask / human cut points are chosen on validation to keep wrong routing under 2% while asking as rarely as possible. They live in config, not in the prompt.

Baselines: keyword rules, and Haiku 4.5 zero-shot. Embeddings come from a Bedrock multilingual embedding model; if none is available in us-east-2, a small ONNX model packaged in the Lambda layer.

M3 · Risk evidence and the lift experiment

Features that compare a charge with the customer's own history, computed in the gold layer: amount vs their median and p95 by category, first time at this merchant, unusual hour or channel, country mismatch, velocity in the last 24 hours, and a login or new-device session shortly before the charge when digital_events can be joined by customer and time.

One-day experiment: LightGBM on is_fraud restricted to transactions with fraud_score ≤ 30 or no score, time-based split, compared with fraud_score alone on PR-AUC and precision at a fixed alert budget, with bootstrap confidence intervals.

  • If lift is significant: M3 becomes an extra lane C trigger at the chosen alert budget.
  • If not (expected, given the v1.4 analysis): M3 stays evidence only. The investigator shows it ("8× your usual amount, first time at this merchant") and the negative result goes in the report.

Learning loop

Every analyst action writes labels: which charge was right, whether the lane was right, whether the recommendation was accepted or edited. A retraining job (SageMaker training job, pay per second) retrains M1 and M2, evaluates the candidate on the frozen test sets, and promotes it only if it beats the current version. For the hackathon we run one demonstration cycle with simulated analyst decisions and label it as such.

The investigator inside the case lifecycle

Each case runs as a small Step Functions state machine. Waiting for the analyst uses a task token, so a case can wait for days at no cost. SLA timers are one-time EventBridge schedules created when the case opens.

Investigator contract

  • Tools (read-only, all through the gateway, scoped to the case's customer): listed in Appendix B.
  • Budget: 12 tool calls, 90 seconds, a token task budget. It stops early when the evidence is sufficient.
  • Output schema: findings, each with the record IDs it rests on; ranked hypotheses (fraud, forgotten purchase, unfamiliar merchant name, duplicate, fee error, pending reversal); one recommendation from a fixed list (reverse fee, open chargeback, block card, explain and close, request information, escalate); confidence; draft reply in the customer's language; open questions.
  • Citation check in code: every cited ID must appear in this run's tool results. Unsupported claims are removed and flagged; if more than one is removed, the report is marked unreliable in the analyst console.
  • No action: the recommendation is a proposal. The analyst approves, edits or rejects, and that choice is logged as a label.

D10

Andrés administers the account and sets up the CDK skeleton. Teammates start without AWS access and build against the interfaces with local backends. When a teammate's slice needs the cloud, they request an IAM user from Andrés and deploy it through the repo's CDK code. Nobody changes AWS by hand in the console. The same pipeline, gateway, model and LLM code runs locally and in the cloud; only the backend behind each interface changes.

Things serverless makes you handle

  • Cold starts. The first request after idle can take 1–3 s. During the judging window a scheduled ping every 5 minutes keeps functions warm for pennies. Provisioned concurrency is skipped because it bills while idle.
  • 30-second API limit. Chat turns must finish well under it. The investigator is asynchronous, so it isn't affected.
  • Package size. Chat Lambda carries LightGBM, NumPy and small model files; keep it well under the 250 MB unzipped limit and load models outside the handler.
  • Not quite zero. Storage (~2 USD/month). In production: WAF (~5 USD/month plus rules). Use Parameter Store (free) instead of Secrets Manager (0.40 USD per secret).

Limits declared in the README

  • Transcripts are templates; all conversation text is generated and labeled synthetic.
  • Complaints don't progress; the case lifecycle is simulated.
  • Portuguese has no real data.
  • Savings figures are estimates and projections, not measured results.
  • The learning loop is demonstrated once with simulated analyst decisions.
